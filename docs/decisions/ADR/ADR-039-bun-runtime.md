# ADR-039: Bun as Runtime, Package Manager and Test Runner

- **Status:** Accepted
- **Date:** 2026-11-05
- **Source:** User decision before Phase 1 ("use Bun, latest version")

## Context

The user wants Bun as the runtime. Environment check on 2026-11-05: Bun upgraded from 1.4.2 to **1.4.4** (latest release, 2026-10-22). The system Node is **v16.14**, too old for Next.js 16 and Vitest. Verified on Bun 1.4.4: `bun:sqlite` (SQLite 3.53.4) with WAL and foreign keys, `Bun.spawn` and `node:child_process` with `detached` plus process-group kill, and `Bun.cron` present.

## Decision

| Concern | Choice |
|---|---|
| Runtime (API, scripts, tooling) | Bun ≥ 1.4.4. Nothing depends on the system Node |
| Package manager / monorepo | Bun workspaces (`bun install`, root `package.json` `workspaces`) instead of pnpm |
| SQLite driver | `bun:sqlite` through `drizzle-orm/bun-sqlite`. Migrations generated by `drizzle-kit` (run with `bunx --bun`) and applied at startup by Drizzle's Bun SQLite migrator |
| Tests | `bun test` (Jest-compatible API) instead of Vitest/Jest. Same test categories: unit, contract, integration, failure-path |
| Frontend | Next.js run under Bun (`bun --bun next dev/build/start`) |
| Child processes | `node:child_process` `spawn(..., { detached: true })` for `claude`, so a timeout or cancel can kill the whole process group (`process.kill(-pid)`) |
| systemd | `ExecStart=%h/.bun/bin/bun …`. `PATH` includes `~/.bun/bin` and `~/.local/bin` (for `claude`); Node isn't needed |
| Version pinning | `packageManager`/`engines` field records the Bun version; setup checks it |

## Consequences

- **Positive:** one fast tool for running, installing, testing and SQLite. Avoids the old system Node entirely.
- **Negative:** some Node-ecosystem tools assume Node. Always invoke them with `bunx --bun` / `bun --bun`, and prefer libraries without native Node addons.
- **Negative:** Next.js on Bun is less battle-tested than on Node. If a problem appears, the web app alone can move to a Node ≥ 20 runtime without affecting the API.
- Supersedes the "Vitest/Jest" testing choice in concept.md §2 and the pnpm assumption in the docs.
