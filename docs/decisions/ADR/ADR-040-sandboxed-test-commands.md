# ADR-040: Sandboxed Test Commands in Develop Runs

- **Status:** Accepted
- **Date:** 2026-11-07
- **Source:** F1 of `docs/superpowers/specs/2026-11-07-followups-batch-1.md` (follow-ups batch 1)

## Context

The develop run (Phase 10, `docs/modules/engineering-tasks.md`) executes the repository's confirmed test command through one `Bash(<testCommand>:*)` grant. Validator rule L limits that grant to a safe test-runner prefix, but the tests themselves are repository code, possibly edited by the model in the same run. Before this decision they ran as the user, with network access and write access everywhere the user can write (`docs/architecture/security-model.md` §3.1, threat model).

Real-CLI findings (2026-11-07, Claude Code 2.1.319, Ubuntu with `kernel.apparmor_restrict_unprivileged_userns=1`, bubblewrap 0.11.1, socat present). Throwaway probes covered writes inside and outside the repository and to `/tmp`, reading a planted secret, child processes, `fetch`, a Docker socket `_ping`, the SSH agent, X11, the runtime directory, `~/.ssh`, `~/.claude`, the Synapse data directory and `/tmp/claude-<uid>`:

- The Claude Code sandbox's seccomp layer fails on this kernel ("nested userns is capability-restricted") unless `network.allowAllUnixSockets: true` is set, which skips that layer. Neither `allowNestedUserNamespaces` nor `enableWeakerNestedSandbox` helps.
- With unix sockets allowed and nothing masked, a test reached the Docker daemon (root-equivalent: the user is in the `docker` group) and saw the SSH agent. Masking with `denyRead` is therefore mandatory. Masking `/run`, `/var/run` and `/tmp` hid the Docker socket, the runtime directory (SSH agent, D-Bus, Wayland) and X11, and a Docker `_ping` failed. `/tmp` became a private writable tmpfs, and masked home directories appeared empty.
- Denying writes to `/tmp` breaks Claude Code's own cwd tracking: every Bash call exits non-zero, which would turn `testsPassed` false. Masking `/tmp` instead, with `TMPDIR` pointed at a private per-run directory re-allowed through `allowRead`, works, and it also hides other Claude sessions' temp files.
- With the final profile: repository writes worked; outside writes, the secret, Docker, the SSH agent, X11 and the network were all blocked; `bun test` passed with a clean exit.

## Decision

| Concern | Choice |
|---|---|
| Contract | `ClaudeJobRequest` and `AIExecutionRequest` carry an optional `sandbox: SandboxSpec` (`{ tmpDir: string; denyRead: string[] }`, `packages/contracts/src/ai.ts`). The zod schema is strict, with at most 64 `denyRead` entries |
| Validator rule M | Runs last, after rule L. An engineering run that grants any `Bash(...)` without a `sandbox` fails with "engineering Bash requires the sandbox". A non-engineering run carrying one fails ("sandbox is for engineering runs only"). `denyRead` must not be empty (the provider appends `/run`, `/var/run` and `/tmp` to it). `tmpDir` and every `denyRead` entry must pass `isSafeAbsolutePath`. `tmpDir` must be neither equal to nor an ancestor of a `denyRead` entry or of `/run`, `/var/run` or `/tmp`, nor inside a `denyRead` entry (see "Observed CLI behaviour"), and not equal to or under `/run` or `/var/run`, because its `allowRead` would re-expose that path (for example `/run/user/<uid>` holds the SSH agent and a rootless Docker socket) |
| Exact settings | When `sandbox` is set, the provider merges exactly this into the `--settings` override: `{ sandbox: { enabled: true, failIfUnavailable: true, autoAllowBashIfSandboxed: false, allowUnsandboxedCommands: false, excludedCommands: [], filesystem: { denyRead: [...denyRead, "/run", "/var/run", "/tmp"], allowRead: [tmpDir] }, network: { allowedDomains: [], deniedDomains: ["*"], strictAllowlist: true, allowAllUnixSockets: true } } }`. `failIfUnavailable` means a missing sandbox fails the run instead of running unsandboxed; `autoAllowBashIfSandboxed: false` and `allowUnsandboxedCommands: false` keep the Bash grant as narrow as rule L made it; the network block denies every domain |
| Fixed masks | `/run` and `/var/run` hide the Docker socket and the runtime directory (SSH agent, D-Bus, Wayland). `/tmp` hides X11 sockets and other sessions' temp files. They are mandatory because `allowAllUnixSockets` skips the seccomp layer, so the masks carry the socket isolation |
| Masks | Under `$HOME`, in this order: `.ssh`, `.gnupg`, `.aws`, `.azure`, `.kube`, `.docker`, `.config`, `.claude`, `.netrc`, `.git-credentials`, `.npmrc`, `.pypirc`, `.cargo/credentials`, `.cargo/credentials.toml`; then the Synapse data directory and the backup directory. No entry is ever dropped. This overrides F1.3's "drop an entry that contains the repository": dropping `~/.config` for a dotfile repository under `~/.config/nvim` would unmask every credential in it (`~/.config/gh/hosts.yml`), and dropping the data or backup directory would expose `synapse.db` and the backups to test code. Such a repository is refused instead (next rows) |
| TMPDIR | Each develop run gets `<run root>/runs/<jobId>`. The run root is per instance: `<cache>/<first 16 hex of sha256(realpath of the data dir)>`, where `<cache>` is `$XDG_CACHE_HOME/synapse` (when absolute) or `~/.cache/synapse`. It is never inside the data directory, and two instances (the service, a smoke, a second dev API) never share it. Every level the step worker creates is `0700`, and `<run root>` and `runs` must be real directories owned by the user. Nothing is created at startup. An in-memory container uses the sibling `<scratchDir>-runs`, created only by a develop run. The run dir is removed when the run ends (also after a throw, timeout or abort; a failed removal is logged with one fixed line and never replaces the run's result or error). Leftovers from a killed process are swept at API start, only from this instance's own `runs/`. `tmpDir` is `<that>/tmp`: created with mode `0700` before the spawn, set as `TMPDIR` in the child env and re-allowed with `allowRead` |
| Repository in a masked path | The develop step refuses, before any run, with the fixed reason `repo_in_masked_path`: a repository whose realpath is at or under `/tmp`, `/run` or `/var/run` (the sandbox would hide it from its own run), and a repository whose realpath is at or inside any mask entry above, such as `~/.config`, `~/.claude`, the data directory or the backup directory (unmasking it would expose credentials, the database or backups) |
| Setting | `engineering.sandbox.enabled` (default `true`, user-editable). Turning it off means **no develop runs, never an unsandboxed one**: the request then carries no `sandbox` and rule M refuses it |
| Failure mapping | A run that exits at startup because the sandbox is unavailable fails the develop step with the fixed reason `sandbox_unavailable`. The task goes to `needs_attention` with the hint "Install bubblewrap and socat (sudo apt install bubblewrap socat), then retry". Sandbox network violations in the tool result do not change `testsPassed`, which still comes from the exit status (ADR-026) |
| Sandbox placeholders | Before the develop run the step records which known placeholder paths exist (below). After the run, whatever its outcome, and before the git-dir fingerprint, diff and unsafe checks, it removes each one that did not exist before and is empty: a zero-byte file where a file is expected, or a directory holding only empty directories. `.claude` goes only when it was absent before and is empty once `.claude/.cc-writes` is gone. Nothing non-empty, pre-existing, a symlink or reached through a symlink is removed (lstat on every component, bounded walks); a kept placeholder is flagged by the fingerprint (`git_dir_changed` → `unsafe_change`) as before. The count is the step output's `sandboxPlaceholdersRemoved`. Filesystem only, in `integrations/repository/sandbox-placeholders.ts` behind `GitWorkflow.sandboxPlaceholders` / `removeSandboxPlaceholders` |
| Health | New check `sandbox`: `ok` when `bwrap` and `socat` resolve on the service PATH; `degraded` with the hint above otherwise; `ok` with detail `disabled` when the setting is off |

## Observed CLI behaviour

Found by the controller's real-CLI develop smoke and probes (2026-11-07, Claude Code 2.1.319), after the first implementation:

- **TMPDIR under a mask breaks every Bash call.** The run scratch first lived in `<data dir>/scratch`, and the data directory is a `denyRead` entry. Re-allowing `tmpDir` with `allowRead` is not enough: bwrap could not create Claude Code's settings file under `TMPDIR` ("Can't create file … Read-only file system"), so every Bash call exited 1 and `testsPassed` was false. The run root therefore moved to the user cache directory, and rule M refuses a `tmpDir` inside any request `denyRead` entry. (The fixed `/tmp` mask differs: the sandbox makes `/tmp` a private writable tmpfs.)
- **The sandbox leaves mount placeholders behind.** To protect `.git`, it mounts over fixed paths and creates an empty target for each one that is missing; they persist after the run. Inside `.git`: `branches/`, `remotes/`, `config.worktree` (0 bytes), `objects/info/alternates` (0 bytes), `objects/info/commit-graphs/`, and `.claude-sandbox-noreplace/` in `info/`, `objects/info/` and `objects/info/commit-graphs/`. At the repository top: `.claude/.cc-writes/`, an empty directory inside a new `.claude/`. The git-dir fingerprint then reported `git_dir_changed` and every develop run ended `unsafe_change`. The develop step now removes exactly these when the run created them and they are empty (the "Sandbox placeholders" row). Any `.claude-sandbox-noreplace` directory under `.git` counts, since the marker can appear in any protected directory. Newer CLI versions may change the set: an unknown placeholder still fails closed as `unsafe_change`.

## Consequences

- **System prerequisites:** bubblewrap and socat become system packages that develop runs need. They are not npm dependencies; the `sandbox` health check reports when they are missing.
- **No network for tests:** a repository whose tests need the network cannot use develop runs. This is recorded in the follow-ups.
- **No seccomp layer:** `allowAllUnixSockets` skips it on kernels that restrict unprivileged user namespaces, so the masks carry the socket isolation. Removing a mask would reopen the Docker socket or the SSH agent.
- **Readable outside the masks:** files outside the masks stay readable by the tests. With no network, writes only inside the repository and the private `TMPDIR`, they can leave only through the diff and the test output, which the user sees before approving the commit.
- **Cache directory:** develop runs write their private `TMPDIR` under `~/.cache/synapse/<instance hash>/runs` (or the same under `$XDG_CACHE_HOME/synapse`). An `XDG_CACHE_HOME` inside a mask entry (for example under `~/.config`) or a data directory placed at the run root makes rule M refuse every develop run.
- **Repositories under `/tmp`, `/run`, `/var/run` or a mask entry** (for example a dotfile repository under `~/.config`, or one inside the Synapse data directory) cannot use develop runs (`repo_in_masked_path`).
