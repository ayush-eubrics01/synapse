# Phase 6b: Away-Mode Auto-Replies — Design

**Authority:** ADR-033 (the decision), ADR-032 (untrusted content isolation), ADR-013 (approvals), ADR-034 (security flags) and the Phase 6b entry gate J1–J5 in `docs/superpowers/plans/2026-11-06-phase-6-followups.md`. J3, real-connector verification, is closed.

## Scope

While away mode is on, Synapse may send three kinds of Slack message **without approval**, only to priority people, after deterministic checks. Every one carries the code-appended tag `Sent using @claude`. When the user switches away mode off, a digest lists everything sent and held.

| Kind | Producer (existing) | Text source | Placement |
|---|---|---|---|
| `acknowledgement` | `message.urgent_detected` (critical/high), from a priority person | Fixed template in code, with no model text | Thread of the urgent message (`threadTs ?? ts`) |
| `stalled_reminder` | `followup.draft_created` with origin `stalled`, where the recipient is the commitment owner | The follow-up draft (model output) | The follow-up's own conversation and thread (R11) |
| `followup_question` | `followup.draft_created` with origin `spec_clarity`, where the recipient is the sender | The spec-clarity draft (model output) | The follow-up's own conversation and thread |

`code_answer` stays out until the repository registry and Engineering Brain exist (Phases 9–10). It is a valid kind name in settings, but nothing produces it.

## Decisions

| # | Decision | Why |
|---|---|---|
| A1 | **A priority person** has a priority of `high` or `critical` in `people_priority_settings`. `normal` is the default and doesn't count | ADR-033 §2: "a manually set priority" |
| A2 | **Away sessions.** `PUT /api/away {on}` starts or ends an `away_sessions` row (`started_at`, `ended_at`) and sets `autoReply.awayMode`. It audits `away.started` / `away.ended` and publishes `away.changed`. Only one session can be open | Gives the digest its time window |
| A3 | **One decision function.** `decideAutoReply(input): AutoReplyDecision` is pure and deterministic. It takes away mode, the kind, the recipient's priority, the incoming text (if any), whether the incoming message has an open warning or high flag, cap counts, confidence, settings and the candidate text. It returns `{ send: true }` or `{ send: false, reason }`, and checks in a fixed order (below) | Testable without a database |
| A4 | **Check order.** The first failure wins, and its reason is recorded: `away_off` → `kind_not_allowed` → `not_priority` → `loop_tag` → `flagged` → `daily_cap` → `thread_gap` → `low_confidence` → `content_secret` → `content_internal_url` → `content_link` → `content_mention` → `content_promise`. Before the policy runs, the service records the pre-check holds of A20 in their own order | The cheapest and most decisive checks go first |
| A5 | **Caps.** At most `autoReply.maxPerPersonPerDay` (default 3) `sent` auto-replies to the recipient in the **rolling 24 h** before now. Separately, no `sent` auto-reply in the same conversation and thread within `autoReply.minMinutesBetweenInThread` (default 30). Counts come from `auto_replies` rows with `decision = 'sent'`. Each evaluation runs as one job in concurrency group `autoreply` (concurrency 1), and the count plus the insert happen in one immediate transaction | J4: thread-safe caps. A rolling window avoids a time-zone setting |
| A6 | **Low confidence.** When a `followup_question` is below `autoReply.minConfidence` (0.75), an `acknowledgement` is sent in its place (if that passes its own checks), and the draft stays in Needs you for approval. A `stalled_reminder` below the threshold is only held, since there is no incoming message to acknowledge. An acknowledgement has no confidence check (fixed text) | ADR-033 §4 |
| A7 | **Spec-clarity confidence.** `specClarityOutputSchema` gains a required `confidence: number 0..1`, which the clarity prompt asks for, and it is stored in `followups.confidence`. Old rows with null confidence count as below the threshold | A followup question needs a confidence to gate on |
| A8 | **Content checks** (`intelligence/auto-reply/content-checks.ts`, pure). These run on the candidate text before the tag is added, for every kind (the fixed acknowledgement text passes them by construction, so in practice they gate the model drafts). Any match means hold. **secret:** `xox[abprs]-`, `sk-[A-Za-z0-9]{16,}`, `AKIA[0-9A-Z]{16}`, `gh[pousr]_[A-Za-z0-9]{20,}`, `-----BEGIN [A-Z ]*PRIVATE KEY-----`, `(?i)\b(password\|passwd\|secret\|token\|api[_-]?key)\s*[:=]\s*\S+`, `\b[A-Z][A-Z0-9_]{2,}=\S{6,}` (an env assignment), and any `[A-Za-z0-9+/_-]{40,}` run. **internal URL:** a URL or host that is `localhost`, `127.*`, `10.*`, `192.168.*`, `172.16–31.*`, `*.local`, `*.internal`, or has a non-default port. **link** (checked after internal URL, so an internal one keeps `content_internal_url`): any `scheme://` (http, https, ftp, ws, mailto, ...), a bare `www.` host, or a Slack `<http…>` / `<mailto:…>` link, raw or entity-escaped. **mention:** `<!channel>`, `<!here>`, `<!everyone>`, `<!subteam^…>` (raw or escaped, with or without a label), any `<@U…>` / `<@W…>` user mention, and any bare `@name` (this covers `@here`, `@channel`, `@everyone`; an email address is not a mention). **promise** (case-insensitive phrases): `I will`, `I'll`, `we will`, `we'll`, `I promise`, `guarantee`, `by (today\|tonight\|tomorrow\|eod\|eow\|monday\|…\|sunday\|next week)`, `deadline`, `I('ve\| have) (approved\|decided)`, `approved`, `go ahead and`, plus dates such as `\b\d{1,2}(st\|nd\|rd\|th)?\s+(jan\|…\|dec)` | ADR-033 §4, kept conservative: a false hold costs little, a false send costs trust. **Note:** `I'll` / `I will` also match normal reminder phrasing. A stalled reminder asks about *their* commitment, so a hit is a real promise worth holding |
| A9 | **Loop tag.** The incoming text contains `sent using @claude` (case-insensitive, whitespace-collapsed, Slack-decoded) | J4 loop guard |
| A10 | **Tag.** `withAutoReplyTag(text) = text.trimEnd() + "\n\nSent using @claude"`, added in code just before the send is requested. The model never sees or writes it | ADR-033 |
| A11 | **Acknowledgement text** (fixed): `"Thanks, I'm away at the moment. I've noted your message and will get back to you as soon as I can."` The tag is added on send. It is written in the first person because it posts as the user | No model text, so nothing to validate |
| A12 | **Policy approval (J1, provenance).** `PromptPart.provenance` gains `policy_approved`. Validator rule K: a `policy_approved` part is allowed **only** in a send run (rule F's single write connector), and never alongside `untrusted` (rule I already covers that). `ApprovalEngine.recordPolicyApproval(tx, request, decidedBy: "auto_reply_policy")` inserts the approval as `approved`, with `decided_by = 'policy'`, audits actor `system` and action `approval.policy_approved`, and publishes `approval.approved`, so the normal execute path runs. It throws unless `action === "slack.auto_reply"`. `slack.auto_reply` is a new action with a permission default of `policy_gated` (a new policy value that only this engine method accepts). The executor gives the send run `policy_approved` provenance for `slack.auto_reply` and `user_approved` for `slack.send` | One execution, verification and needs-attention path for every send. Provenance is never mislabelled |
| A13 | **Revalidate.** The `slack.auto_reply` executor's `revalidate` returns false unless away mode is still on, the auto-reply's session is still the open one, the permission gate is open, **and** no more than `autoReply.maxSendDelayMinutes` (default 15) have passed since the `auto_replies` row was created. The same check runs again in the executor's claim transaction and in `beforeSpawn`. A blocked send is cancelled: outgoing `failed` with `cancelled_away_off` / `cancelled_policy_disabled` / `cancelled_stale`, auto_reply → `held` with reason `away_off` / `policy_disabled` / `stale`. On the revalidate path the approval ends `revoked`; on the claim and `beforeSpawn` paths it ends `failed` (the engine fails it when the executor throws) | The user's return wins; a send that waited too long is no longer timely |
| A14 | **Send guard (J2).** `ClaudeJobRequest` and `AIExecutionRequest` gain `sendGuard?: { toolName: string; expectedInputSha256: string }`. When it is set, `ClaudeCliProvider` builds a **per-run** settings override that adds `hooks.PreToolUse = [{ matcher: toolName, hooks: [{ type: "command", command: "'<bun>' '<abs path>/send-guard-hook.ts' '<sha>' '<toolName>' || exit 2", timeout: 10 }] }]` (every element single-quoted). The hook reads the tool-call JSON from stdin, checks that `tool_name` is `<toolName>`, canonicalises `tool_input` (sorted keys, `thread_ts` omitted when absent) and compares its sha256. On a match it exits 0. Otherwise it exits 2 with the reason `send arguments differ from the approved message` on stderr, which blocks the call. `SlackSender` sets `sendGuard` on **every** send (user and policy). The existing after-the-fact argument check stays as a second layer | J2: prevention before anything goes out |
| A15 | **Proving the hook on the real CLI.** A controller-run smoke (`scripts/dev/hook-smoke.ts`) runs one collector job that allows only the read tool `slack_search_users` behind a guard with a deliberately wrong hash. It passes when the run records a permission denial or block for that tool and no successful tool_result. This is read-only and can never send | Confirms that the CLI honours hooks given through `--settings` with `--setting-sources user` |
| A16 | **Records.** `auto_replies` (`id, session_id, kind, recipient_slack_user_id, conversation_external_id, thread_ts, source_message_id?, followup_id?, decision 'sent'\|'held', reason?, text?, outgoing_id?, approval_id?, created_at`) are recorded. A held row keeps `text` null (the draft lives in its follow-up). Text is kept only for sent rows. **Retention:** the daily `slack.retention_cleanup` job, with the same `retention.slackContentDays`, sets `auto_replies.text` to null on rows whose `created_at` is older than the cutoff; it also blanks `outgoing_messages.text` (to `''`, the column is NOT NULL) on `sent` and `failed` rows, and nulls `followups.draft_text` on `sent`, `discarded` and `failed` rows, older than the cutoff by `created_at`. Non-terminal rows are never touched. Events: `autoreply.sent {autoReplyId}`, `autoreply.held {autoReplyId, reason}`, `away.changed {on}` | Digest source (J5) |
| A17 | **Digest (J5).** `GET /api/away/digest` returns the most recently ended session that hasn't been dismissed: `{ session: {id, startedAt, endedAt}, sent: AutoReplyView[], held: AutoReplyView[] }`, where a view carries the recipient name, kind, conversation label, time, reason and outgoing status. `POST /api/away/digest/:sessionId/dismiss` sets `dismissed_at`. The web shows it as the first Needs-you card ("WHILE YOU WERE AWAY") until dismissed | ADR-033 return digest |
| A18 | **UI.** The header Away switch is enabled. While it is on, a banner reads: "Away mode is on" / "Synapse may auto-reply to your <n> high-priority people, tagged “Sent using @claude”. Everything else waits for you." When n = 0 it reads: "No one is set to high priority, so nobody will get an auto-reply. Everything waits for you." The banner has a "Set priority people" button. The Priority subtitle becomes: "High priority + away mode = auto-reply tagged “Sent using @claude”". A thread message sent by an auto-reply shows "sent via Synapse · auto-reply while away" | Design file |
| A19 | **What is never auto-sent:** urgent-reply drafts (they stay for approval while an acknowledgement goes out), anything to a non-priority person, any `code_answer`, and anything while away is off | ADR-033 kinds |
| A20 | **Pre-checks (final review).** Before `decideAutoReply`, `evaluate` holds, in this order: `missing_context` (the reply cannot be built; a `followup_question` without an origin message also counts), `recipient_mismatch` (DM partner rule), `not_addressed` (acknowledgements only: send-eligible only if the conversation is `im` or `mpim`, the message mentions the user's id as `<@SELF>` / `<@SELF\|name>` / escaped, or the user posted in the same thread, `threadTs ?? ts`, before it), `before_session` (the acknowledged or origin message was sent before the open session started), `already_answered` (the user posted at or after that message in its thread; in an `im` or `mpim`, anywhere in the conversation), `injection_suspected` (the drafting run reported `suspectedInjection.detected`, stored in `followups.suspected_injection`). `before_session` and `already_answered` apply to acknowledgements and follow-up questions; a stalled reminder has no source message. An unknown self id counts as not addressed and as already answered. `flagged` (A3) also covers an open warning-or-higher flag on any message fed into the drafting prompt (`followups.context_message_ids`; null on rows drafted before migration 0014, which keep the other checks) | Only answer what was asked of the user, while they are away, and not what they already handled |

## Out of scope

- `code_answer` producers.
- Approving from a phone (OQ-2).
- Per-person kind settings.
- Changing what an existing draft says.
